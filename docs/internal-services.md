# Внутренние сервисы

Форма HTTP — [openapi-internal.yaml](openapi-internal.yaml). Сервисы доступны только в сети приложения. Заголовка `X-User-Id` у них нет.

Оба принимают необязательный `X-Request-Id` и возвращают его. Оба отдают `GET /health` → `{"status":"ok"}`.

Общее тело ошибки такое же, как у публичного API: `error.code` и `error.message`.

## OCR

`POST /ocr`, `multipart/form-data`, поле `image`.

Одно изображение — одна страница. Ожидается PNG, который собрал Processor. Другой декодируемый растровый формат можно принять, но нераспознанное тело — `400 validation_error`.

Ответ `200`:

```json
{
  "text": "распознанный текст",
  "confidence": 0.92,
  "processing_time_ms": 340
}
```

| Поле | Правило |
|------|---------|
| `text` | Строка. Пустая строка, если символов нет. Это не ошибка HTTP. |
| `confidence` | Число от 0 до 1 либо `null`, если движок не отдал оценку. Processor решение по порогу confidence не принимает. |
| `processing_time_ms` | Время работы движка, целое ≥ 0. |

Движок: PaddleOCR PP-OCRv4, языки `en` и `ru` (`OCR_MODEL=paddleocr_multilingual`). Изображение страницы Processor готовит сам, сервис его не рендерит из PDF.

Таймаут запроса на стороне клиента — `OCR_TIMEOUT` секунд (30). Сервис обрывает разбор по тому же бюджету и отвечает `504 upstream_timeout`.

Модель загружается при старте процесса. Пока она не загружена, процесс не проходит проверку готовности оркестратора; `GET /health` после старта уже предполагает загруженную модель. Если загрузка не удалась, процесс завершается.

GPU не требуется. Если окружение даёт GPU, тот же контракт сохраняется.

## Embedding

`POST /embed`

```json
{
  "texts": ["текст чанка"],
  "input_type": "document"
}
```

`input_type` обязателен: `document` или `query`. Необязательное поле `model`, если передано, должно совпасть с `EMBEDDING_MODEL`. Иначе `400 validation_error`. Клиент не может подменить модель и размерность.

Для `query` сервис до токенизации подставляет строку без изменения текста вопроса:

```text
Instruct: {EMBEDDING_QUERY_TASK}
Query:{text}
```

Между `Query:` и текстом пробела нет: так строка записана в карточке модели. Для `document` текст уходит в модель как есть. Документы и запросы одной пачкой не смешиваются: у пачки один `input_type`.

Ограничения:

| Правило | Ошибка |
|---------|--------|
| `texts` от 1 до `EMBEDDING_BATCH_SIZE` элементов | `400` |
| элемент — строка, после `strip` не пустая | `400` |
| после префикса запроса токенов больше `EMBEDDING_MAX_TOKENS` | `400`. Сервис не обрезает текст сам |

Ответ `200`:

```json
{
  "embeddings": [[0.01, 0.02]],
  "model": "Qwen/Qwen3-Embedding-0.6B",
  "dimension": 1024
}
```

`embeddings[i]` соответствует `texts[i]`. Длина каждого вектора равна `EMBEDDING_DIM`. Вектор — последний непаддинговый токен скрытого состояния, затем L2-нормализация. Mean pooling для этой модели не используется. Токенизатор паддит слева.

Модель: `Qwen/Qwen3-Embedding-0.6B`. Размерность 1024, контекст модели 32768 токенов. Сервис принимает не больше `EMBEDDING_MAX_TOKENS` (1024), чанкер режет документы до `CHUNK_TOKENS` (256). Смена модели требует смены `EMBEDDING_DIM`, пересоздания коллекции и переиндексации. В MVP такого переключения нет.

Веса грузятся в float32 на CPU. Отдельный GPU не требуется. Ориентир по памяти процесса — около 3 ГиБ.

Таймаут клиента на пачку — `EMBEDDING_TIMEOUT` секунд (30 у Processor, 10 у Chat на один вопрос).

Модель загружается при старте. Неудачная загрузка останавливает процесс. Первый запрос не должен платить холодным стартом весов: к моменту готовности веса уже в памяти.

Processor и Chat ходят только на этот сервис. Веса лежат только в Embedding. Токенизатор той же ревизии есть у Processor (нарезка) и у Chat (обрезка длинного вопроса). Ревизия токенизатора и ревизия весов — одна и та же.
