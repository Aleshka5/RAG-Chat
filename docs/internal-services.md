# Внутренние сервисы

Форма HTTP — [openapi-internal.yaml](openapi-internal.yaml). Сервисы доступны только в сети `rag_internal`. Заголовков личности у них нет.

Оба принимают необязательный `X-Request-Id` и возвращают его. Оба отдают `GET /health` → `{"status":"ok"}`.

Общее тело ошибки такое же, как у публичного API: `error.code` и `error.message`.

## OCR

`POST /ocr`, `multipart/form-data`, поле `image`.

Одно изображение — одна страница. Ожидается PNG, который собрал Processor. Другой декодируемый растровый формат можно принять, но нераспознанное тело — `400 validation_error`.

Ответ `200`:

```json
{
  "text": "распознанный текст",
  "confidence": 0.92,
  "processing_time_ms": 340
}
```

| Поле | Правило |
|------|---------|
| `text` | Строка. Пустая строка, если символов нет. Это не ошибка HTTP. |
| `confidence` | Число от 0 до 1 либо `null`, если движок не отдал оценку. Processor решение по порогу confidence не принимает. |
| `processing_time_ms` | Время работы движка, целое ≥ 0. |

Движок: PaddleOCR PP-OCRv4, языки `en` и `ru` (`OCR_MODEL=paddleocr_multilingual`). Изображение страницы Processor готовит сам, сервис его не рендерит из PDF.

Один процесс считает одну страницу одним ядром. PaddleOCR 2.10 передаёт в предиктор `cpu_threads` (по умолчанию 10) через `set_cpu_math_library_num_threads`. У голого Paddle Inference этот параметр равен 1, пока его не задали. `OMP_NUM_THREADS` этот вызов не заменяет: значение математической библиотеки действует на поток, который создал предиктор, а OpenMP на другом потоке берёт переменную окружения или число ядер хоста. Сервис создаёт предиктор и считает страницу на одном и том же потоке, передаёт `cpu_threads=1`, держит `enable_mkldnn` выключенным и выставляет `OMP_NUM_THREADS`, `MKL_NUM_THREADS`, `OPENBLAS_NUM_THREADS` в 1.

Одновременные страницы — отдельные процессы OCR, не пул потоков внутри процесса. Пока Processor один и страницы идут по очереди, вторая реплика простаивает. Она нужна вместе со второй репликой Processor.

Таймаут запроса на стороне клиента — `OCR_TIMEOUT` секунд (30). Сервис обрывает разбор по тому же бюджету и отвечает `504 upstream_timeout`.

Модель загружается при старте процесса. Пока она не загружена, процесс не проходит проверку готовности оркестратора; `GET /health` после старта уже предполагает загруженную модель. Если загрузка не удалась, процесс завершается.

GPU не требуется. Если окружение даёт GPU, тот же контракт сохраняется.

## Embedding

`POST /embed`

```json
{
  "texts": ["текст чанка"],
  "input_type": "document",
  "title": "Отчёт.pdf"
}
```

`input_type` обязателен: `document` или `query`. `title` обязателен для `document` и запрещён для `query`: это имя файла, не заголовок чанка. Необязательное поле `model`, если передано, должно совпасть с `EMBEDDING_MODEL`. Иначе `400 validation_error`. Клиент не может подменить модель и размерность.

Сервис сам собирает строку для модели. Для `query`:

```text
task: question answering | query: {text}
```

Для `document`:

```text
title: {title} | text: {text}
```

Пробелы и разделители именно такие, как в карточке EmbeddingGemma 2 для question answering. Документы и запросы одной пачкой не смешиваются: у пачки один `input_type`. В хранилище чанков и в промпт LLM префикс не попадает: его видит только модель эмбеддингов.

Ограничения:

| Правило | Ошибка |
|---------|--------|
| `texts` от 1 до `EMBEDDING_BATCH_SIZE` элементов | `400` |
| элемент — строка, после `strip` не пустая | `400` |
| после префикса токенов больше `EMBEDDING_MAX_TOKENS` | `400`. Сервис не обрезает текст сам |

Ответ `200`:

```json
{
  "embeddings": [[0.01, 0.02]],
  "model": "google/embeddinggemma-2",
  "dimension": 768
}
```

`embeddings[i]` соответствует `texts[i]`. Длина каждого вектора равна `EMBEDDING_DIM`. Вектор — mean pooling текстовой модели и проекция в 768 измерений, затем L2-нормализация. Усечение до 512, 256 или 128 в MVP не делается.

Модель: `google/embeddinggemma-2`, только текст. Контекст модели 8192 токена, локальное окно внимания 1024. Сервис принимает не больше `EMBEDDING_MAX_TOKENS` (1024), чанкер режет документы до `CHUNK_TOKENS` (512). Смена модели, файла весов или квантования требует пересоздания коллекции и переиндексации. В одной коллекции векторы разных квантований не смешиваются. В MVP такого переключения нет.

## Инференс

Считать вектор можно llama.cpp. Горячий путь — не PyTorch и не загрузка `model.safetensors`.

В контейнере `embedding` два процесса. `llama-server` слушает только `127.0.0.1` внутри контейнера. FastAPI на `EMBEDDING_PORT` принимает `POST /embed`, склеивает префикс и вызывает у llama-server `POST /v1/embeddings`. Наружу сети `rag_internal` виден только FastAPI. Processor и Chat llama-server не вызывают: у OpenAI-совместимого входа нет `input_type` и проверки `title`.

Сборка llama.cpp должна содержать архитектуру `gemma-embedding2` (это есть в llama.cpp с PR 30054, 6 октября 2026). Более старый бинарник останавливается с `unknown model architecture: gemma-embedding2`.

Веса по умолчанию — текстовый GGUF `ggml-org/embeddinggemma-2-GGUF`, файл `embeddinggemma-2-Q8_0.gguf` (около 310 МиБ). Файлы `mmproj-*` не монтируются и флаг проектора не передаётся: изображение и звук в MVP не считаются. F16-весов нет и быть не должно: активации выходят за float16 и дают NaN. BF16-GGUF в том же репозитории есть, на обычном CPU не выбирается.

Запуск llama-server: `--embeddings --pooling mean`. Контекст, batch и ubatch одинаковые и не меньше самой длинной строки пачки. Внимание у модели двустороннее, поэтому короткий ubatch вход не покрывает. Для MVP все три равны `EMBEDDING_CONTEXT` (2048): этого хватает на префикс и `EMBEDDING_MAX_TOKENS`. Параллелизм llama-server на CPU — 1.

Ответ llama-server — уже L2-нормированные векторы длины 768. FastAPI проверяет, что чисел ровно `EMBEDDING_DIM` и среди них нет NaN и бесконечности. Если норма не единица, нормализует сам. Иначе `502`.

`GET /health` адаптера отвечает `200` только после того, как llama-server загрузил GGUF. Неудачная загрузка останавливает контейнер. Первый запрос не платит холодным стартом весов.

Токены для нарезки и для обрезки вопроса считает `tokenizer.json` той ревизии Hugging Face, из которой собран GGUF (файл `.src_sha` в репозитории GGUF). Другой токенизатор даст другую границу чанка.

Отдельный GPU не требуется. Бюджет памяти контейнера — около 2 ГиБ.

Таймаут клиента на пачку — `EMBEDDING_TIMEOUT` секунд (30 у Processor, 10 у Chat на один вопрос).

Processor и Chat ходят только на этот сервис. Веса лежат только в Embedding. Токенизатор той же ревизии есть у Processor (нарезка) и у Chat (обрезка длинного вопроса вместе с префиксом `task: question answering | query: `). Ревизия токенизатора и ревизия весов — одна и та же.
