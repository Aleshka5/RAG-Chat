# Внутренние сервисы

Форма HTTP — [openapi-internal.yaml](openapi-internal.yaml). Сервисы доступны только в сети `rag_internal`. Заголовков личности у них нет.

Оба принимают необязательный `X-Request-Id` и возвращают его. Оба отдают `GET /health` → `{"status":"ok"}`.

Общее тело ошибки такое же, как у публичного API: `error.code` и `error.message`.

## OCR

`POST /ocr`, `multipart/form-data`, поле `image`.

Одно изображение — одна страница. Ожидается PNG, который собрал Processor. Другой декодируемый растровый формат можно принять, но нераспознанное тело — `400 validation_error`.

Ответ `200`:

```json
{
  "text": "распознанный текст",
  "confidence": 0.92,
  "processing_time_ms": 340
}
```

| Поле | Правило |
|------|---------|
| `text` | Строка. Пустая строка, если символов нет. Это не ошибка HTTP. |
| `confidence` | Число от 0 до 1 либо `null`, если движок не отдал оценку. Processor решение по порогу confidence не принимает. |
| `processing_time_ms` | Время работы движка, целое ≥ 0. |

Движок: Surya OCR 2 (`OCR_MODEL=surya-ocr-2`), одна модель на английский и русский. Изображение страницы Processor готовит сам, сервис его не рендерит из PDF.

В контейнере `ocr` два процесса. `llama-server` слушает только `127.0.0.1:8092`. FastAPI на `OCR_PORT` принимает `POST /ocr` и вызывает у llama-server `POST /v1/chat/completions`. Наружу сети `rag_internal` виден только FastAPI.

Веса — `datalab-to/surya-ocr-2-gguf`, ревизия `6a3a4c30e5e74446d4f8b6afd05b2f2da970f470`, файлы `surya-2.gguf` и `surya-2-mmproj.gguf`. Промпт страницы дословный: `OCR this image to HTML. Each block is a div with data-label and data-bbox (x0 y0 x1 y1, normalized 0-1000).` В ответ API попадает текст блоков по порядку модели. Подписи фигур (`Figure`, `Image`, `Diagram`, `Blank-Page`) в текст не входят. `confidence` — средняя вероятность токена, либо `null`, если llama-server её не отдал.

Потолок потоков не задаётся: llama.cpp берёт ядра машины. `--cache-ram -1` снимает потолок кэша (у бинарника иначе 8192 МиБ). `--ctx-size` равен 65536, чтобы картинка страницы и до 24576 токенов ответа не обрезались. `--image-min-tokens` равен 1024. `--reasoning off` выключает след `<think>` у Qwen3.5: с включённым рассуждением страница не заканчивается и упирается в бюджет `OCR_TIMEOUT`. Слои уходят на GPU, если сборка llama.cpp это умеет (`-ngl 999`): для cuda-варианта это работает, для cpu — нет.

Повторяющийся хвост ответа обрывает генерацию сразу: llama-server получает закрытие соединения и снимает слот, не дожидаясь `OCR_TIMEOUT`. Такой ответ один раз переспрашивается при `temperature` 0.2. Если повтор остаётся, в текст страницы попадает только префикс до цикла. Истёкший бюджет без законченного ответа — по-прежнему `504`, обрезанная страница не сохраняется.

Таймаут запроса на стороне клиента — `OCR_TIMEOUT` секунд (120). Сервис обрывает разбор по тому же бюджету и отвечает `504 upstream_timeout`.

Модель загружается при старте процесса. Пока llama-server не здоров, процесс не проходит проверку готовности оркестратора; `GET /health` после старта уже предполагает загруженную модель. Если загрузка не удалась, процесс завершается.

GPU нужен только для скорости. Оба сервиса собираются один раз с целью `cuda` (`localhost/rag-chat_ocr:cuda`, `localhost/rag-chat_embedding:cuda`) и обслуживают оба режима: `OCR_LLAMA_NGL` и `EMBEDDING_LLAMA_NGL` — `999`/`-1` переносят все слои на видеокарту, `0` оставляет их на CPU. Контейнеры и CDI-устройство `nvidia.com/gpu=all` выдаёт Switch-Service, он же переключает режим; пересборки при переключении нет. Контракт HTTP от этого не меняется.

## Embedding

`POST /embed`

```json
{
  "texts": ["текст чанка"],
  "input_type": "document",
  "title": "Отчёт.pdf"
}
```

`input_type` обязателен: `document` или `query`. `title` обязателен для `document` и запрещён для `query`: это имя файла, не заголовок чанка. Необязательное поле `model`, если передано, должно совпасть с `EMBEDDING_MODEL`. Иначе `400 validation_error`. Клиент не может подменить модель и размерность.

Сервис сам собирает строку для модели. Для `query`:

```text
task: question answering | query: {text}
```

Для `document`:

```text
title: {title} | text: {text}
```

Пробелы и разделители именно такие, как в карточке EmbeddingGemma 2 для question answering. Документы и запросы одной пачкой не смешиваются: у пачки один `input_type`. В хранилище чанков и в промпт LLM префикс не попадает: его видит только модель эмбеддингов.

Ограничения:

| Правило | Ошибка |
|---------|--------|
| `texts` от 1 до `EMBEDDING_BATCH_SIZE` элементов | `400` |
| элемент — строка, после `strip` не пустая | `400` |
| после префикса токенов больше `EMBEDDING_MAX_TOKENS` | `400`. Сервис не обрезает текст сам |

Ответ `200`:

```json
{
  "embeddings": [[0.01, 0.02]],
  "model": "google/embeddinggemma-2",
  "dimension": 768
}
```

`embeddings[i]` соответствует `texts[i]`. Длина каждого вектора равна `EMBEDDING_DIM`. Вектор — mean pooling текстовой модели и проекция в 768 измерений, затем L2-нормализация. Усечение до 512, 256 или 128 в MVP не делается.

Модель: `google/embeddinggemma-2`. Текстовый маршрут принимает не больше `EMBEDDING_MAX_TOKENS` (1024), чанкер режет документы до `CHUNK_TOKENS` (512). Контекст модели 8192 токена, локальное окно внимания текста 1024. Смена модели, файла весов или квантования требует пересоздания коллекций и переиндексации. В одной коллекции векторы разных квантований не смешиваются. В MVP такого переключения нет.

`POST /embed` и `GET /health` остаются как описаны выше. `EMBEDDING_DIM` остаётся 768.

## `POST /embed/image`

Тот же процесс FastAPI, только из сети приложения.

```json
{
  "images": ["<base64>"],
  "model": "google/embeddinggemma-2"
}
```

| Правило | Ошибка |
|---------|--------|
| Корень — JSON-объект. Иначе `details.fields` содержит `body` | `400` `validation_error` |
| `images` — массив base64-строк длиной от 1 до `EMBEDDING_MAX_IMAGES` (4). Пустой массив, отсутствие поля и длина сверх лимита называют поле `images` | `400` |
| Строка не декодируется как base64 | `400`, поле `images` |
| После декодирования байтов больше `EMBEDDING_MAX_IMAGE_BYTES` (10485760) | `400`, поле `images` |
| Контейнер не PNG, JPEG, WebP и не GIF | `400`, поле `images` |
| `model` передан и не равен `EMBEDDING_MODEL` | `400`, поле `model` |
| Есть `texts`, `input_type` или `title` | `400`, `details.fields` называет каждое такое поле |

`Content-Type` запроса контейнер не выбирает. Формат читается по сигнатуре декодированных байтов:

| Контейнер | Сигнатура |
|-----------|-----------|
| PNG | `89 50 4E 47 0D 0A 1A 0A` |
| JPEG | `FF D8 FF` |
| GIF | байты `GIF87a` или `GIF89a` |
| WebP | `RIFF` с начала и `WEBP` по смещению 8 |

Изображение уходит в модель без префикса `task` и без `title`. Ответ `200` совпадает с `/embed`:

```json
{
  "embeddings": [[0.01, 0.02]],
  "model": "google/embeddinggemma-2",
  "dimension": 768
}
```

`embeddings[i]` соответствует `images[i]`. Длина 768, L2-норма как у текстового вектора. То же пространство: вектор запроса из `POST /embed` ранжирует точки изображений напрямую. Проверка NaN, бесконечности, длины и нормы — та же, что у `/embed`.

`502` `upstream_failed`: сигнатура принята, но llama-server не декодировал изображение, либо llama-server завершился ошибкой. Сюда же попадает вызов, когда проектор изображения не загружен. `504` `upstream_timeout`: бюджет `EMBEDDING_TIMEOUT` (30 секунд).

`X-Request-Id` возвращается, если заголовок — UUID. Иначе сервис генерирует новый UUID. Это то же правило, что у остальных внутренних маршрутов.

## Инференс

Считать вектор можно llama.cpp. Горячий путь — не PyTorch и не загрузка `model.safetensors`.

В контейнере `embedding` два процесса. `llama-server` слушает только `127.0.0.1` внутри контейнера. FastAPI на `EMBEDDING_PORT` принимает `POST /embed` и `POST /embed/image`. Для текста он склеивает префикс и вызывает у llama-server `POST /v1/embeddings`. Для изображения он передаёт декодированные байты без текстового префикса. Наружу сети `rag_internal` виден только FastAPI. Processor и Chat llama-server не вызывают: у OpenAI-совместимого входа нет `input_type` и проверки `title`, а изображение принимает только `POST /embed/image`.

Сборка llama.cpp должна содержать архитектуру `gemma-embedding2` (это есть в llama.cpp с PR 30054, 6 октября 2026). Более старый бинарник останавливается с `unknown model architecture: gemma-embedding2`.

Веса по умолчанию — текстовый GGUF `ggml-org/embeddinggemma-2-GGUF`, файл `embeddinggemma-2-Q8_0.gguf` (около 310 МиБ). Рядом загружается проектор изображения `EMBEDDING_MMPROJ`, по умолчанию `mmproj-embeddinggemma-2-Q8_0.gguf`, флагом `--mmproj`. Это файл того же набора GGUF. Проектор звука не загружается. F16-весов нет и быть не должно: активации выходят за float16 и дают NaN. BF16-GGUF в том же репозитории есть, на обычном CPU не выбирается. `EMBEDDING_GGUF` остаётся текстовым Q8_0 и не подменяется файлом `mmproj` или F16.

Запуск llama-server: `--embeddings --pooling mean --mmproj <путь EMBEDDING_MMPROJ>`. Контекст, batch и ubatch одинаковые и не меньше самой длинной строки пачки. Внимание у модели двустороннее, поэтому короткий ubatch вход не покрывает. Для MVP все три равны `EMBEDDING_CONTEXT` (2048): этого хватает на префикс и `EMBEDDING_MAX_TOKENS`. Параллелизм llama-server на CPU — 1. Нет файла проектора — текстовый `POST /embed` и `GET /health` живут по-прежнему, а `POST /embed/image` отвечает `502`.

Ответ llama-server — уже L2-нормированные векторы длины 768. FastAPI проверяет, что чисел ровно `EMBEDDING_DIM` и среди них нет NaN и бесконечности. Если норма не единица, нормализует сам. Иначе `502`.

`GET /health` адаптера отвечает `200` только после того, как llama-server загрузил GGUF. Неудачная загрузка останавливает контейнер. Первый запрос не платит холодным стартом весов.

Токены для нарезки и для обрезки вопроса считает `tokenizer.json` той ревизии Hugging Face, из которой собран GGUF (файл `.src_sha` в репозитории GGUF). Другой токенизатор даст другую границу чанка.

Текстовый режим работает и без отдельного GPU. Заявки памяти контейнера embedding: профиль `gpu` — 2304 МиБ VRAM и 1024 МиБ RAM, профиль `cpu` — 1792 МиБ RAM.

Таймаут клиента на пачку — `EMBEDDING_TIMEOUT` секунд (30 у Processor, 10 у Chat на один вопрос).

Processor и Chat ходят только на этот сервис. Веса лежат только в Embedding. Токенизатор той же ревизии есть у Processor (нарезка) и у Chat (обрезка длинного вопроса вместе с префиксом `task: question answering | query: `). Ревизия токенизатора и ревизия весов — одна и та же.
