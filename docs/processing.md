# Обработка и удаление

## Processor

Процесс читает `doc.processing`. LLM он не вызывает.

### Захват

1. Разобрать тело. Неизвестный `schema_version` или битый JSON — `nack` без requeue.
2. Прочитать документ `files` по `file_id`.
3. Нет документа, `user_id` не совпал, `s3_key` не совпал или `content_type` не совпал — `nack` без requeue, статус не трогать.
4. Статус `ready`, `deleting` или `deleted` — `ack`, без обращений к MinIO и Qdrant.
5. Статус `uploaded`, `error` или `processing` — условно выставить `processing`, `error=null`, обновить `updated_at`. Условие фильтра: статус всё ещё один из этих трёх. Если условное обновление никого не задело, перечитать документ и действовать по новому статусу.
6. Пока идёт работа, не реже чем раз в 60 секунд обновлять `updated_at`, только если статус всё ещё `processing`.

### Счётчик доставок

В начале работы с сообщением, после захвата статуса:

- Доставка без флага `redelivered` ставит `checkpoint.process_attempts = 1`. Так начинают первая публикация, sweeper и ручной replay.
- Повторная доставка увеличивает `process_attempts` на 1.
- Значение больше `MAX_PROCESS_ATTEMPTS` (8) — постоянная ошибка `processing_attempts_exceeded`.

Падение процесса не пишет `error` само. Брокер приносит сообщение снова, счётчик растёт на единицу, уже сохранённые страницы и чанки остаются.

Дальше ветка зависит от `content_type` документа MongoDB. `application/pdf` идёт в раздел «Страницы». Тип изображения (`image/jpeg`, `image/png`, `image/webp`, `image/gif`) идёт в раздел «Изображение»: OCR, страницы, `file_pages` и чанки нет. Иной тип отклонён на захвате.

### Страницы

Этот раздел только для `application/pdf`. Файл читается из MinIO по `s3_key`. PDF открывается через PyMuPDF. Файл не открывается — постоянная ошибка `corrupt_pdf`.

Сразу после открытия записать `page_count` и `checkpoint.pages_total`. Оба считают все страницы, включая пустые.

Дальше страницы по порядку, изображения остальных не держать:

1. Запись в `file_pages` для этого `page_number` уже есть — страницу не рендерить и в OCR не слать.
2. Иначе `page.get_text("text")`. Если `len(text.strip()) > MIN_EXTRACTED_CHARS`, записать страницу с `origin=text`. С OCR этот текст не смешивается.
3. Иначе рендер PNG при `OCR_RENDER_DPI` (300) и один запрос в OCR. Повторы: `OCR_MAX_ATTEMPTS` (3), паузы 0,5 с, 1 с, 2 с на таймауте, обрыве сети и HTTP 5xx. HTTP 4xx не повторяется.
4. Ответ OCR с непустым текстом — `origin=ocr`. Успешный ответ с пустым текстом — `origin=empty` и `text=""`.
5. Таймаут или 5xx после всех повторов страницу пустой не помечают. Это временный сбой всей доставки: уже записанные страницы остаются, следующая доставка начнёт с этой.
6. После успешной записи страницы выставить `checkpoint.pages_done` на её номер и обновить heartbeat. Картинка уничтожается.

`pages_done` растёт без дыр, потому что страницы идут по порядку. Падение после записи страницы не повторяет её OCR.

### Чанкинг

Нарезка начинается, когда `pages_done == pages_total`. Параметры: `CHUNK_TOKENS=512`, `CHUNK_OVERLAP_TOKENS=51`. Токены считает токенизатор `EMBEDDING_MODEL` с теми же служебными токенами, с которыми текст пойдёт в модель. Это не `tiktoken` и не деление по словам. В чанк и в payload Qdrant попадает сырой текст, без префикса `title` / `task`. Префикс добавляет Embedding в момент расчёта вектора.

Алгоритм:

1. Для каждой страницы с непустым текстом (`origin` не `empty`) получить список id токенов и запомнить для каждого id номер страницы и `origin`.
2. Склеить списки в порядке страниц.
3. Пустой список — удалить прежние точки этого файла (ноль точек — успех), затем постоянная ошибка `no_extractable_text`. Новые точки не писать. Сбой удаления точек — временный сбой доставки, `error` ещё не пишется.
4. Иначе скользящее окно: `start=0`, `size=CHUNK_TOKENS`, `overlap=CHUNK_OVERLAP_TOKENS`.
5. `end = min(start + size, len(tokens))`.
6. Текст чанка — `decode` id из окна. Если после `strip` текст пуст, чанк не создавать, но окно всё равно двигать.
7. `page_number` — страница первого токена окна, `page_end` — страница последнего.
8. `source = ocr`, если в окне есть токен с `origin=ocr`, иначе `text`.
9. Если `end` упёрся в конец списка, остановиться.
10. Следующий `start = end - overlap`. Он обязан расти хотя бы на 1. При `overlap >= size` процесс не стартует: это ошибка конфигурации.

`chunk_index` назначается только созданным чанкам, с нуля, без дыр.

Пример на 1200 токенах, окно 512, перекрытие 51, шаг 461. Окна: `[0,512)`, `[461,973)`, `[922,1200)`. Третий чанк короче окна. Это нормально.

Перед эмбеддингом записать `checkpoint.chunks_total`, `embedding_model`, `chunk_tokens` и `chunk_overlap`. Если модель или параметры нарезки в контрольной точке другие, точки файла удаляются, `chunks_done` обнуляется, страницы не трогаются. Иначе `chunks_done` — сколько чанков этого списка уже лежит в Qdrant. Повторная нарезка тех же страниц обязана дать те же тексты и те же индексы.

Перекрытие — общие токены соседних окон, а не повторная нарезка строки. Номер страницы берётся из токена, а не «приблизительно с новой страницы».

### Эмбеддинг и запись

В эмбеддинг идут только чанки с индексом от `chunks_done` до конца. Пачка — `EMBEDDING_BATCH_SIZE` (16), `input_type=document`, `title` равен `file_name` из MongoDB. Ответ короче пачки, другой размерности или с числом векторов не по числу текстов — временный сбой, `chunks_done` не сдвигается.

Повтор одной пачки внутри доставки: 3 попытки, те же паузы, что у OCR. Исчерпание попыток — временный сбой доставки, уже записанные предыдущие пачки остаются.

Порядок записи одной пачки:

1. Ещё раз прочитать файл. Если статус уже не `processing`, новые точки не писать. Точки, которые эта доставка уже успела записать, удалить фильтром `user_id` + `document_id` и сделать `ack`.
2. Upsert пачки. Id точки — UUIDv5, см. [data-models.md](data-models.md). Размер запроса к Qdrant не больше `QDRANT_UPSERT_BATCH` (64); пачка эмбеддинга и так меньше.
3. После успешного upsert записать новый `chunks_done`. Падение между upsert и этой записью приведёт к повторному upsert тех же id. Это безопасно.

Когда `chunks_done == chunks_total`, удалить точки файла с `chunk_index >= chunks_total`. Ноль удалённых точек — успех. Так снимается хвост, если прошлый прогон был длиннее.

Затем условный переход `processing → ready`, `error=null`. Если ни один документ не обновлён, точки этого файла удалить и сделать `ack`: файл уже уходит в удаление. `file_pages` при `ready` не удаляются.

`ack` только после перехода в `ready` или после сознательного пропуска (`ready`, `deleting`, `deleted`).

### Изображение

Один файл — одна точка в коллекции `QDRANT_IMAGES_COLLECTION`. Коллекцию Processor создаёт при старте тем же способом, что `documents`: размер 768, расстояние COSINE, HNSW `m=0`, `payload_m=16`, payload-индекс `user_id` с `is_tenant=true` и `document_id` типа keyword. Несовпадение размерности уже существующей коллекции не даёт процессу стартовать.

1. Прочитать байты по `s3_key`. Временный сбой MinIO остаётся временным сбоем доставки.
2. Контейнер определяется по сигнатуре байтов: PNG, JPEG, WebP, GIF. Несовпадение — постоянная ошибка `unsupported_image`. В OCR байты не отправляются, строка `file_pages` не пишется, `page_count` остаётся `null`.
3. Один вызов `POST /embed/image` с одним элементом `images` (base64 этих байтов) и без полей `texts`, `input_type`, `title`. Префикса `task` нет.
4. Ответ `400`, пустой список векторов или вектор не той длины — постоянная ошибка `unsupported_image`. Повтора нет.
5. Ответ `502` или `504`, обрыв сети и недоступность эмбеддера — временный сбой. Внутри доставки три попытки с паузами 0,5 с, 1 с и 2 с, как у пачки текста. Исчерпание попыток оставляет файл в `processing`. После `MAX_PROCESS_ATTEMPTS` пишется `embedding_failed`.
6. Id точки — `uuid5` с именем `{file_id}:0`. Upsert в коллекцию изображений. В `documents` точка изображения не пишется.
7. Payload: `file_id`, `document_id` (равен `file_id`), `user_id`, `file_name`, `s3_key`, `s3_url`, `created_at`. `s3_url` — `s3://{S3_BUCKET}/{s3_key}` без учётных данных. Полей `text`, `page_number`, `chunk_index` и `source` нет.
8. Условный переход `processing → ready`. `page_count` не заполняется. В ответе API `progress` у изображения остаётся `null`. Если статус уже ушёл в удаление, новая точка удаляется фильтром `user_id` + `document_id` и сообщение подтверждается.

`ack` — после `ready` или сознательного пропуска.

### Временный и постоянный сбой

Постоянные: битое тело сообщения, чужой `s3_key`, расхождение `content_type`, `corrupt_pdf`, `unsupported_image`, `image_too_large`, `no_extractable_text`, `processing_attempts_exceeded`. Сначала запись `error`, затем `nack` без requeue. Повтор записи статуса — один. Если записать `error` не удалось, сообщение всё равно уходит в DLQ.

`unsupported_image` покрывает неразобранные байты после скачивания, `400` эмбеддера и пустой вектор. `image_too_large` — объект больше `EMBEDDING_MAX_IMAGE_BYTES`: эмбеддер не вызывается. `502` и `504` эмбеддера постоянными сами по себе не являются.

Временные: MinIO, OCR, Embedding, Qdrant или MongoDB недоступны после коротких повторов шага. Статус остаётся `processing`, контрольная точка не откатывается. Worker спит `min(60, 2^process_attempts)` секунд и делает `nack(requeue=true)`. Следующая доставка продолжает с `pages_done` и `chunks_done`. Пока идёт пауза, канал с `prefetch=1` следующее сообщение не берёт.

Код `embedding_failed` или `index_write_failed` пишется в `error` только вместе с постоянным исходом, то есть когда попытки доставок исчерпаны. До этого файл остаётся `processing`, а причина есть в логе.

## Deletion Worker

Процесс читает `doc.deletion`.

1. Разобрать тело так же строго, как processor.
2. Прочитать документ. Статус `deleted` — `ack`. Документа нет — выполнить шаги 7 и 8 по данным сообщения и затем `ack`. Шаг 8 включает и страницы `file_pages`.
3. Статус `processing` и heartbeat свежий — `nack` без requeue.
4. Если документ есть и `s3_key` другой — `nack` без requeue.
5. Если документ есть и статус не `deleting`, выставить `deleting` условно из `uploaded`, `ready`, `error` и устаревшего `processing`. Это путь повторной доставки. Если условное обновление не прошло, перечитать статус и выбрать ветку заново.
6. Записать `delete_claimed_at`, если оно ещё пустое. Повторная доставка того же сообщения продолжается и при уже заполненном поле: это не блокировка, а отметка «сообщение точно дошло до worker». Пока отметка не записана, объект и точки не удалять. На сбой записи — три попытки, затем сдвинуть `updated_at` и `nack` без requeue: sweeper не поставит новую копию, пока запись снова не состарится на `DELETE_REQUEUE_AFTER_SECONDS`.
7. Удалить объект MinIO. Ответ «нет такого ключа» — успех.
8. Удалить точки Qdrant по `user_id` и `document_id` в коллекции `documents` и в коллекции `images`, и все документы `file_pages` этого `file_id`. Ноль точек и ноль страниц — успех. Ответ «коллекции `images` нет» — тоже успех: коллекцию Deletion Worker не создаёт. Другая ошибка Qdrant остаётся сбоем шага. PDF и изображение чистятся оба, даже если точки были только в одной коллекции.
9. Перевести документ в `deleted`. На этой ветке документ существует: отсутствие документа завершилось на шаге 2.
10. `ack`.

Сбой MinIO или Qdrant после трёх попыток, либо сбой финальной записи MongoDB после одной дополнительной попытки — `nack` без requeue. Статус остаётся `deleting`, `delete_claimed_at` уже заполнен, поэтому sweeper второе сообщение не создаёт. Неподтверждённое сообщение брокер отдаст снова, если процесс умер до `nack`. Сообщение, которое отклонено в DLQ, возвращается только вручную.

Порядок «сначала байты и векторы, потом `deleted`» обязателен. Падение посередине оставляет `deleting`, а повтор дочищает хранилища.

При старте worker выполняет проход sweeper из [messaging.md](messaging.md).

## Чего processor не делает

Не вызывает LLM, не хранит PNG страницы PDF, не принимает решение об удалении файла, не ищет по Qdrant. Текст страницы PDF пишет только в `file_pages`. Для изображения `file_pages` не пишет.
