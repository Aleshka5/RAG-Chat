# Обработка и удаление

## Processor

Процесс читает `doc.processing`. LLM он не вызывает.

### Захват

1. Разобрать тело. Неизвестный `schema_version` или битый JSON — `nack` без requeue.
2. Прочитать документ `files` по `file_id`.
3. Нет документа, `user_id` не совпал или `s3_key` не совпал — `nack` без requeue, статус не трогать.
4. Статус `ready`, `deleting` или `deleted` — `ack`, без обращений к MinIO и Qdrant.
5. Статус `uploaded`, `error` или `processing` — условно выставить `processing`, `error=null`, обновить `updated_at`. Условие фильтра: статус всё ещё один из этих трёх. Если условное обновление никого не задело, перечитать документ и действовать по новому статусу.
6. Пока идёт работа, не реже чем раз в 60 секунд обновлять `updated_at`, только если статус всё ещё `processing`.

### Страницы

Файл читается из MinIO по `s3_key`. Ошибка чтения — статус `error=storage_read_failed`, затем `nack` без requeue.

PDF открывается через PyMuPDF. Файл не открывается — `error=corrupt_pdf`, `nack` без requeue.

Дальше по одной странице, не удерживая изображения остальных:

1. `page.get_text("text")`.
2. Если `len(text.strip()) > MIN_EXTRACTED_CHARS`, страница идёт в чанкинг как `origin=text`. Этот текст больше не смешивается с OCR.
3. Иначе страница рендерится в PNG с `OCR_RENDER_DPI` (по умолчанию 300) и отправляется в OCR одним запросом.
4. OCR повторяется до `OCR_MAX_ATTEMPTS` (по умолчанию 3) с паузами 0,5 с, 1 с, 2 с на сетевой ошибке, таймауте и HTTP 5xx. HTTP 4xx не повторяется.
5. Непустой текст OCR — страница с `origin=ocr`. Пустой ответ и исчерпанные попытки — страница выбрасывается.
6. Изображение после шага уничтожается.

`page_count` равен числу страниц документа, включая пустые, и записывается в MongoDB при финальном обновлении, даже если статус стал `error=no_extractable_text`. Если упали раньше, чем PDF открылся, `page_count` не меняется.

### Чанкинг

Параметры: `CHUNK_TOKENS=120`, `CHUNK_OVERLAP_TOKENS=12`. Токены — wordpiece токенизатора `EMBEDDING_MODEL`, режим `add_special_tokens=false`. Это не `tiktoken` и не деление по словам.

Окно 120 оставляет место для служебных токенов модели: лимит модели 128, вместе с `[CLS]` и `[SEP]` текст должен быть короче.

Алгоритм:

1. Для каждой оставшейся страницы получить список id токенов и запомнить для каждого id номер страницы и `origin`.
2. Склеить списки в порядке страниц.
3. Пустой список — удалить прежние точки этого файла (ноль точек — успех), затем записать `error=no_extractable_text` и сделать `nack` без requeue. Новые точки не писать. Сбой удаления точек — это `index_write_failed`, а не `no_extractable_text`.
4. Иначе скользящее окно: `start=0`, `size=CHUNK_TOKENS`, `overlap=CHUNK_OVERLAP_TOKENS`.
5. `end = min(start + size, len(tokens))`.
6. Текст чанка — `decode` id из окна. Если после `strip` текст пуст, чанк не создавать, но окно всё равно двигать.
7. `page_number` — страница первого токена окна, `page_end` — страница последнего.
8. `source = ocr`, если в окне есть токен с `origin=ocr`, иначе `text`.
9. Если `end` упёрся в конец списка, остановиться.
10. Следующий `start = end - overlap`. Он обязан расти хотя бы на 1. При `overlap >= size` процесс не стартует: это ошибка конфигурации.

`chunk_index` назначается только созданным чанкам, с нуля, без дыр.

Пример на 250 токенах, окно 120, перекрытие 12, шаг 108. Окна: `[0,120)`, `[108,228)`, `[216,250)`. Третий чанк короче окна. Это нормально.

Перекрытие — общие токены соседних окон, а не повторная нарезка строки. Номер страницы берётся из токена, а не «приблизительно с новой страницы».

### Эмбеддинг и запись

Тексты уходят в Embedding пачками по `EMBEDDING_BATCH_SIZE` (32). Ответ короче пачки, другой размерности или с числом векторов не по числу текстов — это `embedding_failed`, без частичной записи точек.

Повтор пачки: 3 попытки, те же паузы, что у OCR. Неудача — удалить уже подготовленное не нужно, потому что upsert ещё не начат; старые точки удаляются непосредственно перед первой пачкой upsert.

Порядок записи:

1. Ещё раз прочитать файл. Если статус уже не `processing` (удаление успело пройти по устаревшему heartbeat), новые точки не писать. Если какие-то точки этого запуска уже попали в Qdrant, удалить их фильтром `user_id` + `document_id` и сделать `ack`.
2. Удалить прежние точки этого файла тем же фильтром.
3. Upsert пачками по `QDRANT_UPSERT_BATCH` (64). Id точки — UUIDv5, см. [data-models.md](data-models.md).
4. Сбой шага 2 или 3 после повторов — `error=index_write_failed`, `nack` без requeue.
5. Условный переход `processing → ready` с `page_count` и `error=null`. Если ни один документ не обновлён, точки этого файла удалить и сделать `ack`: файл уже уходит в удаление.
6. Сбой финальной записи MongoDB после одного повтора — `nack` без requeue. При следующей доставке конвейер выполнится заново.

Только после успешного шага 5 — `ack`.

Ошибка конвейера всегда сначала пытается записать `error`, и только потом делает `nack`. Повтор записи статуса — один.

## Deletion Worker

Процесс читает `doc.deletion`.

1. Разобрать тело так же строго, как processor.
2. Прочитать документ. Статус `deleted` — `ack`. Документа нет — выполнить шаги 7 и 8 по данным сообщения и затем `ack`.
3. Статус `processing` и heartbeat свежий — `nack` без requeue.
4. Если документ есть и `s3_key` другой — `nack` без requeue.
5. Если документ есть и статус не `deleting`, выставить `deleting` условно из `uploaded`, `ready`, `error` и устаревшего `processing`. Это путь повторной доставки. Если условное обновление не прошло, перечитать статус и выбрать ветку заново.
6. Записать `delete_claimed_at`, если оно ещё пустое. Повторная доставка того же сообщения продолжается и при уже заполненном поле: это не блокировка, а отметка «сообщение точно дошло до worker». Пока отметка не записана, объект и точки не удалять. На сбой записи — три попытки, затем сдвинуть `updated_at` и `nack` без requeue: sweeper не поставит новую копию, пока запись снова не состарится на `DELETE_REQUEUE_AFTER_SECONDS`.
7. Удалить объект MinIO. Ответ «нет такого ключа» — успех.
8. Удалить точки Qdrant по `user_id` и `document_id`. Ноль точек — успех.
9. Перевести документ в `deleted`. На этой ветке документ существует: отсутствие документа завершилось на шаге 2.
10. `ack`.

Сбой MinIO или Qdrant после трёх попыток, либо сбой финальной записи MongoDB после одной дополнительной попытки — `nack` без requeue. Статус остаётся `deleting`, `delete_claimed_at` уже заполнен, поэтому sweeper второе сообщение не создаёт. Неподтверждённое сообщение брокер отдаст снова, если процесс умер до `nack`. Сообщение, которое отклонено в DLQ, возвращается только вручную.

Порядок «сначала байты и векторы, потом `deleted`» обязателен. Падение посередине оставляет `deleting`, а повтор дочищает хранилища.

При старте worker выполняет проход sweeper из [messaging.md](messaging.md).

## Чего processor не делает

Не вызывает LLM, не пишет отдельную коллекцию OCR, не хранит PNG, не принимает решение об удалении файла, не ищет по Qdrant.
