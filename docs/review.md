# Разбор черновика

**Статус:** информационный. Норматив — остальные документы в `docs/`.

Черновик от 18.10.2026 в целом задаёт верную систему: PDF, фиксированный чанкинг, асинхронное удаление через RabbitMQ, OCR и эмбеддинги отдельными сервисами, LLM только в чате, поиск по `user_id`, dead-letter, идентификация через `X-User-Id`. Ниже только те места, где черновик противоречит сам себе или не может быть реализован как написан.

Gateway в этот список не входит как задача на разработку: сервис уже есть. В спецификации остался только контракт, который он обязан выполнять.

## Исправления

### 1. Чанк в 1000 токенов не помещается в выбранную модель

`paraphrase-multilingual-MiniLM-L12-v2` имеет `max_seq_length = 128`. Всё, что длиннее, модель молча обрезает. Чанк в 1000 токенов `cl100k_base` ушёл бы в LLM целиком, а в вектор попали бы только первые ~128 wordpiece-токенов. Поиск отвечал бы по началу фрагмента, цитата показывала бы другой текст.

Норматив: токенизатор той же модели, окно **120** токенов (запас под `[CLS]`/`[SEP]`), перекрытие **12** (те же 10%). Размерность вектора остаётся 384, модель не меняется.

### 2. Псевдокод чанкинга теряет overlap

После расчёта overlap ветка «остаток страницы» делает `current_text = [text]` и затирает хвост предыдущего чанка. `page_number` при этом ставится на новую страницу, а не на страницу, с которой хвост реально начался. Алгоритм заменён скользящим окном по токенам с привязкой каждого токена к странице. Цитата использует страницу первого токена чанка.

### 3. Удаление описано тремя несовместимыми способами

- Диаграмма отправляет `doc.delete` из Chat. В разделах про очередь и File Collector отправитель — File Collector.
- `nack(requeue=True)` «с задержкой 5 секунд» RabbitMQ так не умеет: повторная постановка мгновенная, получится горячий цикл. Отдельной delay-очереди в топологии нет.
- «Удалить из MongoDB» соседствует с `status = deleted`. Для идемпотентности нужен надгробный документ, а не физическое удаление.
- Удалять разрешено только из `ready` и `error`, поэтому файл в `uploaded` удалить нельзя.
- Фильтр Qdrant содержит только `document_id`. Для чужого `file_id` этого достаточно лишь пока UUID глобально уникален; в фильтр добавлен `user_id`.
- Требование «удалено больше 0 точек» ломает удаление файла, который ещё не индексировался.

Норматив: публикует File Collector. Пока статус `processing` и heartbeat свежий, API отвечает `409`. Удаление разрешено из `uploaded`, `ready`, `error` и из `processing`, который старше `STALE_PROCESSING_SECONDS`. В MongoDB остаётся запись `deleted`. Нулевой результат в MinIO и Qdrant — успех.

### 4. Гонка processor и deletion

Безусловная запись `status = processing` поверх `deleting` воскрешает файл: worker потом ставит `ready` уже после очистки хранилищ. Переходы делаются условным `findOneAndUpdate`. Перед финальным `ready` processor ещё раз проверяет, что запись всё ещё `processing`. Если за это время файл ушёл в удаление, свежие точки Qdrant стираются.

Зависший `processing` (жёсткое убийство процесса после `nack`, но до записи `error`) закрывается так: processor обновляет `updated_at` не реже раза в минуту, а удаление `processing` разрешено только если метка старше `STALE_PROCESSING_SECONDS`.

### 5. Поиск дубликата по `s3_key` не работает

Ключ содержит новый `file_id` на каждую загрузку, поэтому он никогда не совпадёт. В модель добавлен `content_sha256` и частичный уникальный индекс `(user_id, content_sha256)` для всех статусов, кроме `deleted`.

### 6. Предпросмотр через `#page=` на presigned URL

Фрагмент `#page=5` не является частью HTTP-запроса. Редирект на MinIO обходит авторизацию gateway и требует CORS для PDF.js. Страницу выбирает клиент.

Норматив: `GET /api/files/{file_id}/content` отдаёт байты PDF после проверки `X-User-Id`. Маршрут клиента `/files/{file_id}?page=N` передаёт номер страницы в PDF.js.

### 7. Chat API не может быть одновременно OpenAI-совместимым и продуктовым

У OpenAI Chat Completions нет `chat_id`, владельца и источников. В черновике источники пишутся в MongoDB, но в SSE не отправляются, поэтому карточки под ответом не из чего рисовать. Диаграмма также не показывает вызов Embedding Service из Chat, хотя без вектора вопроса поиск невозможен. В env чата не было `EMBEDDING_URL`.

Норматив: собственный ресурс чатов и поток событий `meta` / `delta` / `done` / `error`. `meta` содержит `chat_id` и `sources` до текста ответа. Клиент к LLM остаётся OpenAI-совместимым и скрыт внутри Chat. Коллекция `chat_settings` убрана из MVP: `top_k` и размер истории задаются окружением.

Пустой результат поиска не отправляется в LLM. Клиент получает фиксированный ответ «Не найдено в документах.» Иначе модель достраивает ответ без контекста.

Заголовок чата — обрезка первого вопроса до 80 символов, не отдельный вызов LLM.

### 8. Очередь описана не до конца

- `x-death` — заголовок AMQP, не поле JSON.
- Очереди `doc.processing.dead` и `doc.deletion.dead` нигде не объявляются и не биндятся.
- `x-max-priority` задан, приоритет сообщений — нет. Приоритет убран.
- Нет `delivery_mode=2` и publisher confirms. Падение между записью в MongoDB и publish оставляет файл без сообщения. File Collector ставит `error=enqueue_failed`, Processor перепубликует только такие записи. Удаление без успешного publish подхватывается, только пока worker его не захватывал (`delete_claimed_at` пустой), чтобы отклонённое в DLQ сообщение не порождало новые копии.
- OCR одной страницы в таблице ошибок пропускается, а семантика `ack` требует успеха «всех шагов, включая OCR». Норматив: сбой одной страницы не валит сообщение; если индексировать нечего, статус `error` / `no_extractable_text`.
- Идентификаторы точек Qdrant не заданы. Повторная обработка без стабильного id плодит дубликаты. Id детерминированный: UUIDv5 от `file_id` и `chunk_index`. Перед записью точки этого файла заменяются целиком.
- Эмбеддинг в конвейере вызывается по одному чанку, хотя API принимает пачку. Запись в Qdrant то «одним запросом», то «пачками по 64». Норматив: эмбеддинг пачками по 32, upsert по 64.

### 9. Извлечение текста страницы

Порог «больше 50 символов → чанкуем» смешан с документо-уровневым чанкингом. Короткий текстовый слой плюс OCR в одну строку добавляет мусор колонтитула к распознанному тексту.

Норматив: на странице либо извлечённый текст (если символов больше порога), либо только текст OCR. Пустая страница в индекс не попадает. Отдельные значения `source = missing | empty` не хранятся. `source` чанка — `text` или `ocr` (если в окно попал хотя бы один OCR-токен).

Имя файла в `s3_key` берётся как есть и допускает `../`. В ключе — очищенное имя, исходное имя остаётся в `file_name`. Приём файла дополнительно проверяет сигнатуру `%PDF`, а не только `Content-Type`.

### 10. Мелочи, которые меняют реализацию

- «Идентификентность» — идемпотентность. Пропуск повторной обработки только для `ready`, `deleting`, `deleted`. `error` и `processing` обрабатываются снова, иначе повтор после падения невозможен.
- «Вычитка файлов по одному» — это `prefetch=1` на канале consumer, а не глобальный лок кластера.
- Мультиязычность RU+EN уже есть у выбранных OCR и embedding-модели. Из roadmap убрана.
- У ошибок не было общего тела, пагинации, `/health` и `X-Request-Id`. Они заданы в API.
- Внутренние OCR и Embedding без аутентификации. Их нельзя публиковать наружу; с ними говорит только сеть приложения.

## Что сохранено без изменений

PDF как единственный формат MVP, адаптеры форматов как будущее расширение, LLM не вызывается из Processor, поиск по всем файлам пользователя, dead-letter без автоматического replay, Qdrant с `is_tenant=true` на `user_id` и HNSW `m=0` / `payload_m=16` (это действующая схема multitenancy Qdrant ≥ 1.11), PaddleOCR для `en+ru`, модель эмбеддингов и размерность 384, порядок очистки MinIO → Qdrant → финальная запись MongoDB, подтверждение сообщения только после согласованного результата.
